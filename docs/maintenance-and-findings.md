# 维护流程与后续经验

整理日期：2026-11-16；待验证项于 2026-11-17 更新。下面按日期区分历史代码审查、用户截图、配置比较与推断；11 月 17 日的规则变更和实测另见 [直连规则收紧](rule-tightening.md)。

## 1. 原生订阅与 DNS 跟随版的对比

2026-11-13 用户提供的 Net.Coffee Claude 检测页对比：

| 项目 | 原生海豚湾 | DNS 跟随版 |
|---|---|---|
| “中国 IPv4 出口”栏 | 国内联通出口 | 日本代理出口 |
| Cloudflare / Claude 出口 | 日本代理出口 | 同一个日本代理出口 |
| 页面显示的 DNS 解析器 | 国内电信 | Cloudflare |

这些是用户截图和反馈，未由 Agent 切回原生现场重测。同日只读比较电脑上的配置文件，得到：

- 原生常规 DNS 为订阅提供的三个自定义 DoH，上游未显式绑定手动选择组；跟随版改为 `https://1.1.1.1/dns-query#实际选择组`。
- 原生 `proxy-server-nameserver` 指向本机 DNS 监听端口；跟随版改为独立引导解析器。
- 手机跟随 YAML 保留原生全部 2,473 条规则，顺序相同；Mac 版仅在原规则前增加六条 Typeless / 向日葵相关直连规则，总计 2,479 条。国内 GeoIP 直连规则均保留。

- 当时 Game 日本节点参数相同。原生订阅与本地副本的其他少量节点 / 流量标签不同，说明本地副本不是原生订阅自动更新后的镜像。
- 没有为 `2026.ip138.com`、`my.ip.cn` 专门增加代理规则；配置对应的 Merge / Script 也未额外修改这些规则。

以上为 11 月 13 日快照。11 月 17 日 Mac 撤销 105 条非必要直连例外后为 2,374 条；手机未随之修改。不要将两个日期的数量混用。

**已确认 DNS 配置发生改变；尚未还原探针出口变化的完整因果链。** DNS 答案或缓存影响后续 GeoIP 判断是排查方向，但缺少原生测试当时的连接记录，不写成已确定原因。正常使用不必为补齐解释而反复切回原生。

手机比较对象是电脑上保存的导入文件，不代表重新读取了手机运行配置。两端直连 DNS 策略也不同：手机文件将常规和直连解析都绑定代理；Mac 文件保留国内直连 DoH 与业务域名例外。电脑策略由用户选择的直连业务决定，不应机械照搬手机。

## 2. 订阅更新不能覆盖定制配置

“DNS 跟随”是从原订阅复制的独立本地 YAML。不要把更新原生订阅理解成已经同步修订本地副本，也不要期待本地配置的更新按钮自动合并修改。

推荐顺序：

1. 完成任务，退出使用这条网络的 Claude 客户端；记录配置、末级节点及当前出口，备份已验收副本。
2. 更新保留的原生远程订阅，不自动切换正在使用的本地配置。
3. 从新版原生配置生成新的本地候选，重新合并 DNS、IPv6 和用户选择的直连规则 / DNS 例外，保留旧版回滚。
   同时重新应用经用户确认的直连例外删除清单，检查新版新增规则与组选择；只恢复 DNS 修改会遗漏后续收紧策略。
4. 先用当前 Mihomo 校验，再加载候选；核对节点存在、选择组最终指向与实际出口。按操作手册完成验收后再打开 Claude。
5. 手机单独生成 / 导入适合手机的文件并验收，不能用电脑结果替代。维护不要求重复注册、安装或充值。

更新内容可能包含节点新增 / 下线 / 改名、地址、端口、认证或协议参数、代理组、规则、DNS、流量和到期信息。只变流量标签通常不改变出口；当前节点参数变化、节点被移除或组改选可能改变出口，加载配置也可能重建连接。供应商还可能在不更新订阅时调整后端，所以节点名称相同不保证 IP 永久相同。

## 3. 检测请求与账号登录不是一回事

2026-11-13 检查到的 Net.Coffee 页面脚本从本站跨站 `fetch` 请求 `https://claude.ai/cdn-cgi/trace`，未设置 `credentials: "include"`，也未提供账号令牌。标准 `fetch` 默认凭据模式为 `same-origin`，该请求不会自动携带另一个站点的 Claude 登录 Cookie。

这说明当时检查到的请求不是带登录 Cookie 的账号请求；不代表第三方检测没有访问 Claude，也不代表今后所有版本都一样。真正打开 Claude 网页时可使用该站登录状态，故首次配置前清理旧站点数据、登录时核对账号仍有作用。不要读取或公开任何人的 Cookie 和账号历史来证明这一点。

如果以后要专门比较原生与跟随配置的普通分流，限定测试到已确认的非 Claude 探针并记录实际规则链；不要误开会主动访问 Claude 的综合检测页。此类测试需先结束相关会话，不得在使用期间切配置。

## 4. CheckCC 误报案例

会话中对当时 CheckCC 线上 JavaScript 的审查发现：它用宽泛正则扫描整条 WebRTC candidate 文本，并把含冒号且未命中几个排除前缀的字符串当成公网 IPv6，没有完整验证地址格式。

离线模拟一条只含内网地址的候选信息时，`candidate:3321303803` 被截出 `e:3321303803`，进而被计作公网 IP；该字符串不是合法 IPv4 / IPv6。用户截图中的单条告警恰为此形式。此结论来自当时线上代码与离线复现，不代表做了实际 WebRTC 路径验收，也不能扩展为今后所有告警都误报。

当时公开 GitHub 仓库没有覆盖线上网络检测的完整实现。Agent 只读取源码 / 页面脚本并离线复现，没有安装依赖或启动项目；临时下载材料随后按用户要求删除。复用此案例应引用 [项目来源](https://github.com/yacuo/check-cc)，重新核对版本，不传播“评分等于真实封号概率”的说法。
